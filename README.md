# k3k-rancher-ui

A minimal, community Rancher UI extension for creating and managing
[k3k](https://github.com/rancher/k3k) virtual clusters on community (non-Prime) Rancher.

It adds a **Virtual Clusters** product to any Rancher-managed cluster that has the
k3k CRDs installed (for example a Harvester host running the k3k operator).

## Features

- List k3k `Cluster`, `VirtualClusterPolicy` and `ETCDSnapshot` resources, with status from `.status.phase`
- Create / edit form for clusters: mode (shared / virtual), servers, agents, K3s version,
  persistence (storage class + size) and API exposure (LoadBalancer / NodePort / Ingress)
- **Download KubeConfig** action, reading the admin kubeconfig Secret k3k writes for each cluster
- Full YAML create/edit for anything the form doesn't cover
- Delete clusters

Not included (yet): automatic import of a virtual cluster into Rancher — see
[Importing into Rancher](#importing-a-virtual-cluster-into-rancher).

## Requirements

- Rancher 2.10 or newer (UI extensions v3)
- The k3k operator installed on the host cluster:

  ```bash
  helm repo add k3k https://rancher.github.io/k3k
  helm install k3k k3k/k3k -n k3k-system --create-namespace
  ```

## Install in Rancher

1. In Rancher, open **Extensions** → ⋮ → **Manage Repositories** → **Create**
2. Target: **http(s) URL to an index generated by Helm**
   Index URL: `https://badamsz.github.io/k3k-rancher-ui`
3. Back on **Extensions → Available**, install **k3k Virtual Clusters** and reload the page
4. Open the host cluster; **Virtual Clusters** appears in the side nav

## Usage

**Create:** Virtual Clusters → Clusters → Create. Pick a namespace (one per cluster
is a good convention, e.g. `k3k-rustdesk`), the mode and node counts, then Create.

**Shared vs virtual mode:** shared mode runs workloads as pods on the host via
virtual-kubelet. Virtual mode gives each cluster its own k3s agents, but those agent
pods currently run **privileged** on the host — a privileged pod inside the virtual
cluster is effectively privileged on the host node. Prefer shared mode on a hypervisor
host like Harvester unless you need the extra isolation.

**Kubeconfig:** once the cluster is `Ready`, use the row action **Download KubeConfig**.
The server address in it is whatever k3k exposed (service / LoadBalancer / NodePort);
pick an exposure type reachable from where you'll run `kubectl`.

## Importing a virtual cluster into Rancher

1. Download the kubeconfig (above)
2. Rancher → **Cluster Management** → **Import Existing** → **Generic**, give it a name, **Create**
3. Run the registration command shown, against the virtual cluster:

   ```bash
   KUBECONFIG=./mycluster-kubeconfig.yaml kubectl apply -f https://<rancher>/v3/import/<token>.yaml
   ```

## Development

Requires Node 24 and Yarn 1.

```bash
yarn install
API=https://your-rancher yarn dev   # dashboard with the extension at https://localhost:8005
yarn build-pkg k3k-rancher-ui       # production build into dist-pkg/
yarn test
```

Code lives in `pkg/k3k-rancher-ui/`:

| Path | Purpose |
| --- | --- |
| `product.ts` | Registers the Virtual Clusters product and its resource types |
| `models/k3k.io.cluster.js` | State badge from `.status.phase`, Download KubeConfig action |
| `edit/k3k.io.cluster.vue` | Create / edit form |
| `types.ts` | Resource type IDs and option lists |

## Releasing

Publishing uses Rancher's reusable workflow (`.github/workflows/build-extension-charts.yml`),
which builds the extension, commits the Helm chart and assets to the `gh-pages` branch,
and updates `index.yaml`.

1. Bump `version` in `pkg/k3k-rancher-ui/package.json` and commit
2. Create a GitHub release whose tag is exactly `k3k-rancher-ui-<version>`
   (e.g. `k3k-rancher-ui-0.1.0`) — other tags are rejected by the workflow
3. Rancher picks up the new version on the next repository refresh

One-time repo setup: the `gh-pages` branch must exist, **Settings → Pages** must serve
from `gh-pages` (root), and **Settings → Actions → General → Workflow permissions** must
be *Read and write*.
