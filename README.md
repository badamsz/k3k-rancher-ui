# k3k-rancher-ui

A minimal, community Rancher UI extension for creating and managing
[k3k](https://github.com/rancher/k3k) virtual clusters on community (non-Prime) Rancher.

It adds a **Virtual Clusters** product to any Rancher-managed cluster that has the
k3k CRDs installed (for example a Harvester host running the k3k operator).

## Features

- List k3k `Cluster`, `VirtualClusterPolicy` and `ETCDSnapshot` resources, with status from `.status.phase`
- K3s version picker listing the releases your Rancher supports (same list as Cluster
  Management), or "match host cluster"
- Create / edit form for clusters: mode (shared / virtual), servers, agents,
  persistence (storage class + size) and API exposure (LoadBalancer / NodePort / Ingress)
- **Download KubeConfig** action, reading the admin kubeconfig Secret k3k writes for each cluster
- Full YAML create/edit for anything the form doesn't cover
- **Automatic import into Rancher** when creating a cluster, or later via the
  **Import into Rancher** action; **Open in Rancher** jumps to the imported cluster
- Delete clusters (also removes the linked Rancher cluster and its import Secret)
- **Server health** panel on the cluster detail page: stuck etcd finalizers, lost quorum, servers sharing a host node, undersized volumes
- **Spread servers across host nodes** option (pod anti-affinity via `spec.serverAffinity`)
- **Release Stuck Server Pods** and **Expand Server Volumes** recovery actions (see [Keeping HA clusters alive](#keeping-ha-clusters-alive-through-host-maintenance))

## Requirements

- Rancher 2.10 or newer (UI extensions v3)
- The k3k operator installed on the host cluster:

  ```bash
  helm repo add k3k https://rancher.github.io/k3k
  helm install k3k k3k/k3k -n k3k-system --create-namespace
  ```

## Install in Rancher

1. In Rancher, open **Extensions** → ⋮ → **Manage Repositories** → **Create**
2. Target: **http(s) URL to an index generated by Helm**
   Index URL: `https://badamsz.github.io/k3k-rancher-ui`
3. Back on **Extensions → Available**, install **k3k Virtual Clusters** and reload the page
4. Open the host cluster; **Virtual Clusters** appears in the side nav

## Usage

**Create:** Virtual Clusters → Clusters → Create. Pick a namespace (one per cluster
is a good convention, e.g. `k3k-rustdesk`), the mode and node counts, then Create.

**Shared vs virtual mode:** shared mode runs workloads as pods on the host via
virtual-kubelet. Virtual mode gives each cluster its own k3s agents, but those agent
pods currently run **privileged** on the host — a privileged pod inside the virtual
cluster is effectively privileged on the host node. Prefer shared mode on a hypervisor
host like Harvester unless you need the extra isolation.

**Kubeconfig:** once the cluster is `Ready`, use the row action **Download KubeConfig**.
The server address in it is whatever k3k exposed (service / LoadBalancer / NodePort);
pick an exposure type reachable from where you'll run `kubectl`.

## Importing a virtual cluster into Rancher

Leave **Import into Rancher** checked on the create form (optionally set the Rancher
cluster name; it defaults to the k3k cluster name). The extension then:

1. Creates an *Imported* cluster in Rancher (`fleet-default/<name>`) and fetches its
   registration manifest
2. Stores the manifest in a Secret `rancher-import-<k3k-name>` next to the k3k Cluster
3. Adds that Secret to the Cluster's `spec.addons`; k3k mounts addons into the k3s
   server's auto-deploy manifests directory, so the virtual cluster installs
   `cattle-cluster-agent` itself and registers with Rancher
4. Annotates the k3k Cluster with `k3k-rancher-ui.badamsz.github.io/rancher-cluster`
   so the two stay linked
5. Sets `rancher.io/imported-cluster-version-management: "false"` on the Rancher cluster.
   Rancher upgrades imported K3s clusters with system-upgrade-controller on each node,
   which doesn't apply to k3k's pod-based servers; change the version from the k3k
   cluster's edit form instead. **This matters in shared mode:** virtual nodes mirror the
   host nodes, so upgrade jobs would be scheduled onto the real host. Clusters imported
   before 0.3.0 can be fixed with the **Disable Rancher Version Management** row action

For a cluster that already exists, use the **Import into Rancher** row action. Adding
the addon makes k3k roll the server StatefulSet, so the action is only offered for
`Ready` clusters with **dynamic** persistence (an ephemeral cluster would lose its data
on the restart).

Requirements:

- Pods in the virtual cluster must be able to resolve and reach Rancher's **server-url**
  (Global Settings → `server-url`)
- If Rancher uses a private CA, the registration manifest already carries the CA checksum;
  nothing else to configure

Manual alternative: download the kubeconfig, then Rancher → Cluster Management →
Import Existing → Generic, and apply the registration command against the virtual cluster.

## Known issues

### Rancher's Kubectl Shell doesn't start on shared-mode clusters

Upstream: [rancher/k3k#168](https://github.com/rancher/k3k/issues/168) (open, no fix yet).

When a **shared-mode** virtual cluster is imported into Rancher, **Kubectl Shell** on the
imported cluster never connects. Rancher's `dashboard-shell-*` pod in `cattle-system`
stays in `ContainerCreating` or times out and disconnects because its `admin-kubeconfig` ConfigMap volume can't be synced. k3k's virtual-kubelet fails to create the host copy of the
`impersonation-shell-admin-kubeconfig-*` ConfigMap, so the pod never gets the volume.

The rest of the Rancher integration still works (cluster explorer, workloads, and so on).


This extension can't fix the bug. Until upstream does, use one of these:

- Use **Download KubeConfig** on the k3k cluster and run `kubectl` locally, or download the kubeconfig from the imported cluster in Rancher
- Use **virtual** mode if you need the in-browser shell. The bug report covers shared mode only. See the privileged-pod caveat under [Usage](#usage) first

## Keeping HA clusters alive through host maintenance

k3k HA clusters (3+ servers) run embedded etcd in the server pods, and have a few sharp
edges when the host drains or reboots nodes (for example during a Harvester upgrade).
The cluster's detail page shows a **Server health** panel that flags these.

| Problem | Symptom | What the extension does |
| --- | --- | --- |
| All servers deleted at once; k3k can't remove their etcd members because the virtual API is down | Server pods stuck in `Terminating` on `etcdpod.k3k.io/finalizer`; node drains hang (Harvester upgrade stuck at **Pre-drained**) | Flags stuck pods; **Release Stuck Server Pods** action |
| etcd peer URLs are pod IPs, and each restart changes the IP | After a node reboot, servers elect forever (`dial tcp <old-ip>:2380: i/o timeout`) | Flags lost quorum and servers sharing a node; see the runbook below |
| Each time a server's member is removed and the pod comes back, k3s keeps a `server/db/etcd-backup-*` copy; the default volume is 2G | `no space left on device` in a server's log, then crash loops | Create form defaults to 10Gi; flags volumes under 5Gi; **Expand Server Volumes** action |
| Two servers on one host node | Rebooting that node takes etcd below quorum | Flags it; **Spread servers across host nodes** (required pod anti-affinity, on by default for new HA clusters) |

Before draining or rebooting a host node:

1. Open each virtual cluster's detail page and check that every server is ready and no
   warnings are shown
2. Drain one node at a time, and wait for all servers to be ready again before the next

### Recovering etcd quorum

Check which servers' API actually works (`Ready` only means the port is open):

```bash
kubectl -n <ns> exec k3k-<name>-server-0 -- kubectl get --raw /readyz
```

**A server is a member, but etcd has its old IP** (it logs `this server is not a member of the
etcd cluster. Found [... https://<old-ip>:2380 ...]`): update its peer URL from a healthy
server, using a throwaway etcdctl container that borrows that server's certificates:

```bash
R=/proc/1/root/var/lib/rancher/k3s/server/tls/etcd
kubectl -n <ns> debug k3k-<name>-server-1 --image=quay.io/coreos/etcd:v3.6.0 \
  --target=k3k-<name>-server --profile=general -- \
  etcdctl --endpoints=https://127.0.0.1:2379 --cacert=$R/server-ca.crt \
  --cert=$R/server-client.crt --key=$R/server-client.key \
  member update <member-id> --peer-urls=https://<new-pod-ip>:2380
```

(Run it once with `member list -w table` instead to find the member IDs.)

**A server was removed from etcd but still has its old data** (the others have quorum; it
isn't in `member list`, and its log only shows `dial tcp <old-ip>:2380` timeouts). It never
learns it was removed, so restarting it doesn't help. Make it re-join as a new member:

```bash
kubectl -n <ns> exec k3k-<name>-server-N -- sh -c \
  'cd /var/lib/rancher/k3s/server/db && mv etcd etcd-stale && mkdir -m 700 etcd'
# restart the container by stopping k3s (PID 1 is a shell and ignores SIGTERM)
kubectl -n <ns> exec k3k-<name>-server-N -- sh -c \
  'for p in /proc/[0-9]*; do case "$(tr "\0" " " < $p/cmdline)" in "/bin/k3s server"*) kill ${p#/proc/};; esac; done'
```

Leave the **empty** `db/etcd` directory in place: if it is missing on server-0, k3k's startup
script bootstraps a brand-new cluster instead of joining, and you get two etcd clusters.
Delete `etcd-stale` once the server is back in `member list`.

**No two servers can reach each other** (every server is electing): rebuild from one server.

1. Take Longhorn (or CSI) snapshots of all server volumes
2. Set `spec.servers: 1`. k3k restarts server-0 in single-node mode, and its startup
   script runs `k3s server --cluster-reset` on the existing data. Server pods that hang in
   `Terminating` can be released with **Release Stuck Server Pods**
3. With server-0 serving, move `server/db` aside on the other server volumes (for example from
   a one-off pod that mounts the PVC); keep `server/token` and `server/tls`
4. Set `spec.servers` back to 3. The other servers join as new members

Pick the server whose data is newest for step 2. If that isn't server-0, copy its
`server/db` onto server-0's volume first, otherwise you roll back to server-0's state.

Clean up afterwards: `server/db/etcd-backup-*` directories and anything you moved
aside are not removed automatically.

## Development

Requires Node 24 and Yarn 1.

```bash
yarn install
API=https://your-rancher yarn dev   # dashboard with the extension at https://localhost:8005
yarn build-pkg k3k-rancher-ui       # production build into dist-pkg/
yarn test
```

Code lives in `pkg/k3k-rancher-ui/`:

| Path | Purpose |
| --- | --- |
| `product.ts` | Registers the Virtual Clusters product and its resource types |
| `models/k3k.io.cluster.js` | State badge, Download KubeConfig / Import into Rancher / Open in Rancher / recovery actions, linked delete |
| `detail/k3k.io.cluster.vue` | Detail page with the Server health panel |
| `utils/server-health.js` | Server pod / volume health checks (stuck finalizers, quorum, co-location, volume size) |
| `utils/rancher-import.js` | Creates the Rancher cluster, fetches the manifest, writes the addon Secret |
| `edit/k3k.io.cluster.vue` | Create / edit form |
| `types.ts` | Resource type IDs and option lists |

## Releasing

Publishing uses Rancher's reusable workflow (`.github/workflows/build-extension-charts.yml`),
which builds the extension, commits the Helm chart and assets to the `gh-pages` branch,
and updates `index.yaml`.

1. Bump `version` in `pkg/k3k-rancher-ui/package.json` and commit
2. Create a GitHub release whose tag is exactly `k3k-rancher-ui-<version>`
   (e.g. `k3k-rancher-ui-0.1.0`) — other tags are rejected by the workflow
3. Rancher picks up the new version on the next repository refresh

One-time repo setup: the `gh-pages` branch must exist, **Settings → Pages** must serve
from `gh-pages` (root), and **Settings → Actions → General → Workflow permissions** must
be *Read and write*.
